# 基于规则引擎的反诈信息核验与风险解释系统 软件需求规格说明书



---

## 1. 引言

### 1.1 编写目的

本文档定义"基于规则引擎的反诈信息核验与风险解释系统"（以下简称"本系统"）的功能需求与非功能需求，作为系统设计、实现、测试与毕业设计验收的依据。

### 1.2 项目背景

电信网络诈骗手法持续演化，用户缺乏对可疑短信、聊天内容、链接、电话号码与网址的便捷核验手段。本系统以规则引擎为最终裁决核心，以大语言模型与文本相似度模型为辅助手段，对待检内容给出风险等级判定，并提供全程可回溯的证据链与解释。

### 1.3 术语与名词约定

本文档及以下所有设计、开发、测试文档中，下列名词应保持唯一含义，不得混用：

| 名词         | 定义                                  |
| ---------- | ----------------------------------- |
| 待检内容       | 用户提交给本系统核验的短信文本、聊天文本、链接说明、电话号码或网址   |
| 风险等级       | 判定结论的四级分级：**安全 / 低风险 / 中风险 / 高风险**  |
| 规则         | 由"条件 + 权重 + 解释模板"构成的判定单元，存储于规则库     |
| 证据链        | 一次判定中"原文 → 抽取事实 → 命中规则 → 分数构成"的完整记录 |
| 判定轨迹       | 证据链的结构化数据形式，供解释生成与审计使用              |
| 命中规则       | 对某次待检内容条件成立、参与评分的规则                 |
| 黑白名单       | 已确认安全（白）或已确认涉诈（黑）的号码、域名、IP 名单       |
| 案例库        | 公开诈骗案例的集合，用于相似案例检索与知识库浏览            |
| 降级         | 大语言模型或向量检索不可用时，系统自动切换为纯规则模式的机制      |
| 攻击成功率（ASR） | 攻击变体样本绕过检测的比例                       |
| 用户         | 提交待检内容、查看判定结果的系统使用者                 |
| 运营人员       | 维护规则库、黑白名单与处理反馈的管理侧使用者              |

### 1.4 措辞约定

- **应 / 须**：强制要求，对应任务书中的核心功能（P0），验收时必须全部满足；
- **宜**：建议要求，对应增强功能（P1），验收时应说明取舍情况；
- **可**：可选要求，对应选做功能（P2），不作为验收必要条件。

## 2. 总体描述

### 2.1 产品定位

本系统是一个面向个人用户的反诈信息核验工具与面向运营人员的规则运营平台的组合体，同时提供攻防测试能力以支撑实验评估。

### 2.2 用户角色

| 角色 | 主要职责 |
|------|----------|
| 用户 | 提交单条或批量待检内容，查看风险等级、证据链与解释，反馈误报/漏报 |
| 运营人员 | 维护规则与黑白名单、配置评分阈值、处理反馈样本、查看管理看板 |
| 实验人员 | 使用攻防测试平台生成变体样本、执行批量回放评估、产出盲区报告 |

### 2.3 系统边界

- 本系统**应**对待检内容给出风险等级与解释，**不**代替用户执行拦截、举报等处置动作；
- 大语言模型**不得**持有最终风险裁决权，仅用于信息抽取、解释生成与测试样本生成；
- 最终风险结果**须**保留可回溯的规则证据链。

### 2.4 技术约束

依据任务书约定，本系统的实现受以下约束（属环境约束，具体技术方案设计文档另行规定）：

- 后端应采用 FastAPI（Python 3.11）；
- 数据库生产与验收环境应采用 PostgreSQL；开发与演示环境可采用 SQLite 以简化部署；
- 大语言模型应通过外部 API 接入（DeepSeek / 通义千问等，具体选型在实现阶段确定），系统不得依赖某一特定模型服务商，且须支持可替换与降级；
- 向量检索应采用 FAISS，相似度模型采用 BGE 中文预训练模型；
- 前端建议采用 Vue 3 + Element Plus + ECharts；
- 规则应采用声明式 JSON DSL 表达，运营人员可通过配置维护规则而不修改代码。

### 2.5 假设与依赖

- 大语言模型服务通过外部 API 获得，其可用性不在本系统控制范围内，故系统须具备完整降级机制；
- 案例库初始数据来源于公开渠道收集，规模不少于 500 条；
- 规则库初始规模为 30–50 条规则。

## 3. 功能需求

### 3.1 核验主流程（用户侧）

#### 3.1.1 文本核验

- **描述**：用户应能提交短信、聊天文本或链接说明，系统应返回风险等级、命中规则与解释。
- **前置条件**：无。
- **主流程**：输入待检文本 → 提交 → 系统判定 → 展示风险等级、命中规则与解释。
- **验收标准**：对测试集中的每条样本文本，系统均返回唯一的风险等级、至少零条命中规则列表及对应解释；无命中规则时返回"安全"并说明理由。

#### 3.1.2 号码/网址核验

- **描述**：用户应能提交电话号码或网址，系统应结合黑白名单与特征库给出判定。
- **前置条件**：黑白名单与特征库已初始化。
- **主流程**：输入号码或网址 → 提交 → 系统比对黑白名单与特征库 → 返回判定结果。
- **验收标准**：命中黑名单的号码/网址判定为高风险；命中白名单的判定为安全；均未命中时依据特征规则判定，三类情形各有对应测试用例通过。

#### 3.1.3 批量核验

- **描述**：用户应能上传 CSV 或 TXT 文件进行批量检测，系统应返回汇总结果；单文件样本量不超过 1000 条、体积不超过 2 MB，超限文件应被拒绝并提示原因。
- **主流程**：选择文件 → 上传 → 系统逐条检测 → 返回每条结果及汇总统计。
- **验收标准**：上传 100 条样本的合法文件，全部样本均有判定结果，汇总统计（各级风险数量）与逐条结果一致；格式非法的文件应被拒绝并提示原因。

#### 3.1.4 结果分级展示

- **描述**：系统应将判定结果按安全/低风险/中风险/高风险四级展示，不同等级使用不同颜色与图标区分；判定为高风险时，系统应给出"建议不要操作"的提示。
- **验收标准**：四个等级各有样例，页面展示的颜色与图标互不相同；所有高风险结果的页面均出现"建议不要操作"提示。

#### 3.1.5 判定路径回放

- **描述**：系统应将证据链按"原文 → 抽取事实 → 逐条规则命中 → 分数构成"的步骤逐步可视化展示。
- **验收标准**：对任意一条已判定的记录，回放展示的每一步内容与该记录的判定轨迹数据一致；命中多条规则时逐条展示，不得合并或省略。

### 3.2 规则库管理（运营侧）

#### 3.2.1 规则维护

- **描述**：运营人员应能对规则进行新增、查询、修改、删除、启用与停用操作。
- **前置条件**：以运营人员身份登录。
- **验收标准**：六类操作各有测试用例通过；被停用的规则不参与后续判定。

#### 3.2.2 规则热更新

- **描述**：规则的新增、修改、启停应在不重启系统的前提下生效。
- **验收标准**：修改某规则权重后不重启服务，再次提交命中该规则的样本，判定分数按新权重计算。

#### 3.2.3 规则冲突检测

- **描述**：系统应对规则库进行静态分析，检测规则遮蔽与规则冗余，并向运营人员告警。
- **验收标准**：构造含已知遮蔽关系与冗余关系的规则集，系统告警应覆盖全部预设冲突，且不应将无冲突规则误报告警。

#### 3.2.4 黑白名单管理

- **描述**：运营人员应能维护电话号码、域名、IP 的黑名单与白名单。
- **验收标准**：三类条目（号码、域名、IP）均可增删改查；名单变更后即时影响 3.1.2 的判定结果。

#### 3.2.5 评分阈值配置

- **描述**：运营人员应能配置风险分级的分数阈值与语义层加权系数。
- **验收标准**：修改阈值后，同一分数样本的等级划分随新阈值变化；修改加权系数后，同一输入的总分按新系数合成。

### 3.3 信息抽取与风险判定（引擎侧）

#### 3.3.1 实体抽取

- **描述**：系统应从待检内容中抽取电话号码、银行卡号、网址、金额、App 名称五类实体。
- **验收标准**：在实体抽取测试集上，五类实体的抽取准确率达到实验报告规定指标（见第 5 章 E2）。

#### 3.3.2 文本预处理

- **描述**：系统应在判定前对输入执行全半角统一、常见变形还原（如"VX"还原为"微信"）与超长文本分段处理。
- **验收标准**：含全角字符、变形词、超长内容的样本经预处理后判定结果与其标准形态一致；变形还原词表可维护。

#### 3.3.3 语义意图识别

- **描述**：系统应识别待检内容的骗局类型与话术特征（施压、恐吓、利诱等），输出受结构化格式约束；识别失败或服务不可用时，系统应自动降级且不影响规则判定。
- **验收标准**：构造意图识别服务不可用场景，系统仍返回完整规则判定结果并在结果中标注降级状态；意图识别输出格式非法时同样触发降级。

#### 3.3.4 规则全量匹配

- **描述**：系统应将抽取得到的事实表对当前启用的全部规则进行匹配，输出命中规则及对应证据片段。
- **验收标准**：每条命中规则均可给出其在原文中的证据片段；证据片段须为原文的真实子串。

#### 3.3.5 相似案例检索

- **描述**：系统应检索案例库中与待检内容最相似的 Top-K 历史案例（K=5，余弦相似度阈值 0.75），作为辅助证据。
- **验收标准**：返回结果不超过 K 条且按相似度降序排列；检索服务不可用时系统降级，不影响规则判定。

#### 3.3.6 风险评分分级

- **描述**：系统应将规则得分与语义加权得分合成为总分，按阈值输出四级风险等级，并生成完整判定轨迹。
- **验收标准**：总分 = 规则分 + 语义加权分的计算过程在判定轨迹中逐项可查；每条判定记录均生成完整判定轨迹，无缺失字段。

### 3.4 解释与知识库

#### 3.4.1 知识库浏览

- **描述**：用户应能按骗局类型浏览典型案例与防范建议。
- **验收标准**：每个骗局类型分类下至少有一条案例与一条防范建议；分类列表与案例库数据一致。

#### 3.4.2 模板化解释

- **描述**：系统应能基于命中规则的解释模板生成解释文本；该能力不依赖任何外部模型服务。
- **验收标准**：断开全部外部模型服务后，每条判定结果仍附带完整模板解释；模板解释包含全部命中规则的说明。

#### 3.4.3 通俗解释生成（P1）

- **描述**：系统宜基于判定轨迹与相似案例生成用户版与技术版双视角解释；解释中引用规则与案例时须标注其编号。
- **验收标准**：同一判定记录可分别获取两个视角的解释；解释中出现的每个规则编号与案例编号均能在规则库或案例库中查到。

#### 3.4.4 解释引用校验（P1）

- **描述**：系统宜校验生成解释中的引用是否真实存在；校验失败时，系统应自动降级为模板解释。
- **验收标准**：构造含虚构编号的解释文本，系统检出全部虚构引用并回退为模板解释，且向用户展示的结果中不含虚构引用。

### 3.5 反馈、审计与管理看板

#### 3.5.1 误报/漏报标记

- **描述**：用户应能对判定结果标记"误报"或"漏报"，被标记的记录应进入待处理队列。
- **验收标准**：标记操作后，记录出现在待处理队列中，且关联原始判定记录可追溯。

#### 3.5.2 反馈驱动规则维护

- **描述**：运营人员应能查看待处理队列中的反馈样本，并据此修订规则。
- **验收标准**：从待处理队列可跳转至对应判定轨迹与规则编辑入口；反馈处理状态（待处理/已处理）可更新。

#### 3.5.3 全链路审计日志

- **描述**：系统应对每次判定的输入、事实表、模型原始输出、判定结果全量留痕。
- **验收标准**：任意抽取一条历史判定记录，其输入、事实表、模型原始输出（如有）、判定结果四项均可完整查询；日志不可由前台操作修改或删除。

#### 3.5.4 管理看板

- **描述**：系统应以图表形式展示规则命中率、风险类型分布与检测量趋势。
- **验收标准**：三类图表的数据与审计日志统计结果一致；时间范围可筛选。

### 3.6 攻防测试平台（P1）

#### 3.6.1 变体样本生成

- **描述**：系统宜支持生成三类攻击变体样本：字符级（谐音、拆字、emoji 插入）、语义级（改写、方言化）、拼接级（多轮拆分）。
- **验收标准**：每类变体均可批量生成并可追溯其原始样本。

#### 3.6.2 注入样本生成

- **描述**：系统宜支持生成提示词注入样本（如"忽略规则""输出评分 0"类指令）。
- **验收标准**：注入样本集可批量生成并标注注入类型。

#### 3.6.3 批量回放评估

- **描述**：系统宜支持将变体样本批量送检，统计攻击成功率与检出率变化。
- **验收标准**：对同一变体样本集，攻击前后的检出率、攻击成功率均有统计输出，数据与逐条判定记录一致。

#### 3.6.4 盲区报告

- **描述**：系统宜按"骗局类型 × 攻击手法"生成检出率热力图，定位规则盲区。
- **验收标准**：热力图覆盖全部已测骗局类型与攻击手法组合，数值与回放评估结果一致。

#### 3.6.5 规则迭代建议

- **描述**：系统宜基于漏检样本分析给出规则补充建议；建议经人工审核后方可入库。
- **验收标准**：未经人工审核的建议不出现在生效规则库中；审核通过的建议可追溯其来源样本。

#### 3.6.6 注入防御

- **描述**：系统应具备输入隔离、输出校验、架构裁决三层防护，并支持防御前后对比实验。
- **验收标准**：注入样本集在防御开启前后的攻击成功率均有统计，防御开启后攻击成功率显著下降（具体指标见第 5 章 E5）。

### 3.7 对话助手（P2）

- **描述**：系统可支持对话式交互，包括口语化提交待检内容、针对判定报告追问解释、基于案例库的反诈咨询。
- **约束**：对话助手仅可通过工具调用与确定性引擎交互，不得参与最终判定。
- **验收标准**：对话提交与表单提交对同一内容返回一致的判定结果；追问与咨询的回答引用可追溯。

### 3.8 扩展接入（P2）

- **描述**：系统可支持录音经转写后接入既有文本核验流程。
- **验收标准**：录音样本经转写核验后，其判定流程与直接文本提交的判定流程一致，核心流程代码无改动。

## 4. 非功能需求

| 编号 | 类别 | 需求 | 验收标准 |
|------|------|------|----------|
| N1 | 可解释性 | 每条风险结论应可回溯到具体规则、证据片段与相似案例；解释中的引用应可验证 | 随机抽取 20 条判定记录，每条均可完整回溯，引用验证全部通过 |
| N2 | 鲁棒性 | 大语言模型服务或向量检索服务任一不可用时，系统应自动降级，核心检测能力不得中断 | 分别断开两类服务，3.1.1 与 3.1.2 功能仍正常返回判定结果 |
| N3 | 可审计性 | 系统应全链路留痕，支持事后复盘与误报漏报分析 | 见 3.5.3 验收标准 |
| N4 | 性能 | 单条文本核验端到端响应时间应不超过 3 秒；不含模型解释时应不超过 500 毫秒；批量 100 条核验应不超过 60 秒 | 在测试环境对规定样本量实测，指标全部达标 |
| N5 | 安全性 | 系统应通过输入隔离与输出校验抵御提示词注入；大语言模型不得具有最终裁决权 | 注入测试集上防御开启后，模型输出无法改变规则裁决结果 |
| N6 | 可扩展性 | 规则应支持热更新；新增输入形态（如语音）应通过转写接入，不得改动核心判定流程 | 见 3.2.2、3.8 验收标准 |
| N7 | 可维护性 | 规则应以声明式 DSL 表达，运营人员应能通过配置维护规则，无需修改代码 | 运营人员在不接触源码的条件下完成规则新增并生效 |

## 5. 实验与验收测试

系统验收应包含以下实验，实验方法与样本规模在实验方案中另行细化：

| 编号  | 实验     | 验收要点                               |
| --- | ------ | ---------------------------------- |
| E1  | 规则正确性  | 规则命中准确率 ≥ 90%；空文本、超长文本、混合内容等边界条件通过率 100% |
| E2  | 抽取有效性  | 实体抽取总体准确率 ≥ 90%（App 名称类可放宽至 ≥ 80%）；意图识别准确率 ≥ 85%；降级触发正确率 100% |
| E3  | 相似度层贡献 | 纯规则与"规则+相似案例检索"两种模式的召回率对比（重点为新型变体），相似度层带来的新型变体召回率提升 ≥ 10 个百分点 |
| E4  | 红蓝对抗   | 攻击前检出率 ≥ 90%；字符级变体攻击成功率 ≤ 30%、语义级变体攻击成功率 ≤ 50%；产出盲区热力图与规则迭代前后对比 |
| E5  | 注入防御   | 注入样本防御开启后攻击成功率 ≤ 5%，且较防御前相对下降 ≥ 50% |
| E6  | 解释完整性  | 模板解释与生成解释的引用准确率 100%；用户理解度评测 ≥ 4 分（5 分制） |
| E7  | 性能测试   | 单条/批量延迟、降级模式性能满足 N4；并发 ≥ 10 请求无错误 |
